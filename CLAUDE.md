# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A fork of [j-hc/revanced-magisk-module](https://github.com/j-hc/revanced-magisk-module): a Bash-based builder that downloads stock Android APKs, applies ReVanced (or compatible: Morphe, Piko) patches via the ReVanced CLI, and packages the result either as non-root APKs or as Magisk/KernelSU modules. It is driven entirely by `config.toml` and runs daily in GitHub Actions.

There is no compiled application source here — the "code" is shell scripts plus prebuilt helper binaries. The patches and CLI themselves are fetched at build time from upstream GitHub releases.

## Commands

```bash
./build.sh                      # build everything enabled in config.toml
./build.sh config.toml          # explicit config (also accepts a .json config)
./build.sh clean                # remove temp/, build/, build.md, patches-built.json
./build.sh config.toml --config-update   # print a trimmed config of apps with newer patches available (used by CI to decide whether to build)
```

Requirements: `jq`, OpenJDK **21+**, `zip` (build.sh checks these and aborts if missing — though its check only verifies `java` *exists*, not its version). OpenJDK 21 is a hard requirement in practice: the Morphe CLI (`MorpheApp/morphe-cli`, the default `cli-source` for almost every app) is compiled for Java 21 (class file version 65.0) and dies on Java 17 with `UnsupportedClassVersionError … only recognizes class file versions up to 61.0`, failing every Morphe-patched build. On Termux, `build-termux.sh` bootstraps the environment and handles output to `/sdcard/Download`.

There is **no test suite and no linter**. To validate changes, run a build with a single app enabled (set `enabled = false` on the rest in `config.toml`, or `enabled = true` on just one). `NORB=true` skips rebuilding APKs that already exist in `temp/`/`build/` — useful when iterating on module-packaging logic without re-patching.

## Architecture

Three files do all the work:

- **`build.sh`** — entry point. Parses `config.toml`, resolves per-app settings (with main-table defaults), fetches CLI + patches prebuilts once per source, then spawns `build_rv` in the background for each app/arch, throttled to `parallel-jobs`. `arch = "both"` fans out into two builds (arm64-v8a + arm-v7a).
- **`utils.sh`** — the engine. Everything else lives here: TOML parsing, GitHub/HTTP downloads, the four download backends, version resolution, patching, and module packaging. `build.sh` is mostly config plumbing around `utils.sh`'s `build_rv`.
- **`module/`** — the Magisk/KernelSU module template. Copied per-build into `temp/`, filled with `module.prop` + `config`, and zipped. `customize.sh` is the on-device installer (runs at flash time, not build time): it installs the correct stock version, mounts the patched `base.apk` over the real one via bind mount, and handles arch/version checks.

### The build pipeline (`build_rv` in utils.sh)

1. **Resolve package name** by probing download sources for the app.
2. **Resolve version** per `version` mode: `auto` picks the highest version supported by all included patches (parsed from CLI `list-versions` output), stepping down to the next-highest supported version if the top pick can't be downloaded (see the auto step-down gotcha below); `latest`/`beta` take the newest from the download source; a literal version is used as-is.
3. **Download stock APK** by trying each configured `*-dlurl` source in `DL_SRCS` order (`direct`, `archive`, `apkmirror`, `uptodown`). Bundles (`.apkm`/`.xapk`) are merged into a single APK via APKEditor and re-signed.
4. **Verify signature** against `sig.txt` (skips apps not listed there).
5. **Patch** via `patch_apk` → ReVanced CLI, signing with `ks.keystore`.
6. **Package** for each build mode:
   - `apk` (non-root): the microg/gmscore patch is *included*; output goes straight to `build/`.
   - `module` (root): the microg patch is *excluded* (the module mounts over the real app, so it relies on the stock signature); the patched APK plus optional stock APK are zipped with the module template.

### Download backends

Each source implements the same informal interface — `get_<src>_resp`, `get_<src>_pkg_name`, `get_<src>_vers`, and `dl_<src>` — so `build_rv` can iterate over `DL_SRCS` generically. apkmirror/uptodown scrape HTML using the `htmlq` binary; archive/direct parse URLs. Adding a source means adding these four functions and an entry to `DL_SRCS`.

### Prebuilt binaries (`bin/`)

`set_prebuilts` selects arch-specific binaries by `uname -m`: `tq` (TOML→JSON, the `$TOML` parser), `htmlq` (HTML scraping), `aapt2` (Termux/Android only). `paccer.jar` + `dexlib2.jar` strip ReVanced integrations checks from the patches bundle when `remove-rv-integrations-checks = true`. `apksigner.jar` signs APKs. Module installer ships a per-arch `ksu_profile` binary.

## Configuration (`config.toml`)

The main (top-level) table sets defaults; each `[App]` table overrides them. Keys are documented in `CONFIG.md`. Two gotchas:

- Patch names in `excluded-patches`/`included-patches` must be quoted, and a single quote *inside* a patch name is escaped by doubling it (`'Hide ''Get Music Premium'''`).
- `toml_get` returning non-zero means "key absent" — the `|| DEFAULT` idiom throughout `build.sh` depends on this, so it's load-bearing, not sloppy error handling.

## CI (`.github/workflows/`)

`ci.yml` runs daily on cron: it checks out `patches-state.json` from the `update` branch and runs `--config-update` to see if any enabled app has newer patches; only then does it call `build.yml`. **The app list is computed once, in `ci.yml`'s `check` job, and passed to `build.yml` as the `update_cfg` workflow_call input** (a multi-line `GITHUB_OUTPUT` heredoc), which writes it verbatim to `config.json`. `build.yml` no longer recomputes it — see the CI-decision gotcha below. `build.yml` builds, uploads APKs/modules to a GitHub Release tagged with an incrementing version code, regenerates `*-update.json` files and `patches-state.json` on the `update` branch (the JSONs power in-app Magisk module updates), and optionally posts to Telegram. The `update` branch is data, not code — it holds `build.md` (the release-notes changelog), `patches-state.json` (the per-app build-decision state), and the per-module update JSONs.

**`patches-state.json` — the build-decision state (fork-specific).** `config_update` decides whether an app needs a rebuild by comparing the *current* patch-bundle asset for each of its sources (primary + `extra-patches-source`) against what that app was *last successfully built with*, recorded per app in `patches-state.json` (`{ "<table>": { "<patches-source>": "<asset-name>" } }`). This replaced an earlier design that grepped `build.md`. The problem with `build.md`: it's regenerated from scratch each run holding **only that run's built subset**, so once a different subset built and overwrote it, apps that had fallen out of `build.md` looked un-recorded and got rebuilt unconditionally every day (spurious `versionCode` churn with identical versions). `patches-state.json` is instead **merged, not overwritten** — `build.yml` folds this run's `patches-built.json` into the existing state with `jq -s '.[0] + .[1]'`, so earlier runs' apps keep their record. Two deliberate semantics: (1) state is written **only on a successful build** (`build_rv` records via `log_built_patches` after an artifact is produced; a failed build stays un-recorded → retried next run — matching how `*-update.json` is only written for shipped modules); (2) an app not in the state (newly added, or never-successfully-built) always rebuilds. Because state is keyed per app and covers apk-only apps too (recorded regardless of build mode), the apk-only + `extra-patches-source` gaps that made a naive "compare against `*-update.json`" approach lossy don't apply. A source the GitHub/GitLab API can't resolve is treated as "no change" so a transient API error never triggers a full rebuild.

**The recorded asset name is the *normalised* one — both sides must agree (upstream sync, 2026-09-07).** `get_prebuilts` renames every patches asset it downloads to `patches-<tag without leading v>.<ext>` before writing it, so the local filename no longer depends on how a source names its release asset. Two consequences that must stay in step: (1) `log_built_patches` records `basename` of that on-disk file, so `patches-state.json` holds the **normalised** name; (2) `_latest_patches_name` — which produces the value `_patches_src_changed` compares against — reads the raw API asset name and therefore **applies the same `patches-<ver>.<ext>` transform itself**. If either side is changed without the other, the comparison can never match and **every enabled app rebuilds on every run** — precisely the `versionCode` churn `patches-state.json` exists to prevent. At the time of the sync all six configured sources already named their assets `patches-<ver>.<ext>`, so normalisation was a no-op and no rebuild was triggered; a future source that names its asset differently (say `piko-3.9.0.mpp`) is the case this alignment covers. The same rename is why the cached-file branch parses `cut -d'-' -f2-` (not `-f3-`) for `tag_name`, and why the cache lookup `*patches-${name_ver#v}.*` hits at all.

**Reserved control keys in `patches-state.json`.** A per-app entry is normally `{ "<patches-source>": "<asset-name>" }`. Every patches source holds a `/` (`owner/repo`, `gitlab:owner/repo`). **A per-app key *without* a `/` is thus a reserved control key, not a source.** Only one exists: **`_pending`**, an array of `{version, arch, built}` that records an `auto` step-down (see the step-down note that follows). Nothing enumerates `.[$t] | keys` — `_patches_src_changed` looks up `.[$t][$s]` by exact source name — so a control key is inert to the source comparison. Control keys ride the ordinary pipeline: `build_rv` → `temp/pending-versions.tsv` → folded into `patches-built.json` by `build.sh` → merged by `build.yml`. **`build.yml` and `ci.yml` need no changes for this.** The merge is shallow (`.[0] + .[1]` replaces the whole per-app object), so a control key that a build no longer writes **self-clears** at that build. The fold is guarded on purpose: only an app that *also* has a built row gets a control key. Without that guard, a build that downloaded the apk but then failed to patch it replaces the whole entry of that app with a control key alone. That **wipes its recorded bundle assets**.

**Telegram notifications.** All Telegram posts go through `.github/scripts/tg-notify.sh` (curl wrapper; no-ops if `TG_TOKEN`/`TG_CHAT` env is empty). Two destinations, one bot (`TG_TOKEN` secret): the **public** release announcement in `build.yml`'s "Report to Telegram" step posts to `TG_CHAT` (var); the **admin** notifications post to `TG_CHAT_ADMIN` (var). Admin gets a daily heartbeat from `ci.yml`'s `notify` job (`if: always()`, reads `needs.check/build.result` → built/skipped/failed) and a build-failure alert from `build.yml`'s `Report failure to Telegram` step (`if: failure() && !inputs.from_ci`, so CI-triggered failures are reported once by `ci.yml`, not duplicated). Failure messages are minimal — a line plus the Actions run URL. Two per-app admin digests also post from `build.yml` (`if: always()`, each no-ops when its file is empty): `Report per-app build failures` reads `failed-builds.txt` (`record_failure`), and `Report per-app build warnings` reads `build-warnings.txt` (`record_warning`) — the latter flags non-fatal caveats on apps that *did* ship, currently just `auto` builds that stepped down below their latest supported version (see the auto step-down gotcha). Both also append a table to the job summary.

## Maintenance gotchas (learned operationally)

- **Forcing a rebuild (full or per-app).** `ci.yml` only builds when an enabled app's current patch-bundle asset differs from what `patches-state.json` on the `update` branch records for it — it ignores config changes that don't touch a patch bundle (e.g. a new `version` pin, changed dlurls, an `include-stock` mode switch). *Adding* an app does trigger it (a table absent from the state always rebuilds). To force a complete rebuild of everything, delete `patches-state.json` from the `update` branch; `config_update` then writes an empty state, every enabled app looks new, and the emitted config lists them all. To rebuild **specific** apps without touching the rest, delete just their keys from `patches-state.json` on `update` (a table absent from the state always rebuilds — `_patches_src_changed` sees `recorded=""` ≠ latest): branch off `update`, `jq 'del(."App-Table", …)'` the keys out, and PR back. This rebuilds each such app in **all** its build modes — the decision is per-app, not per-mode. (Deleting `build.md` no longer forces a rebuild — it's release-notes only now.) `jq 'del(."App-Table")'` drops the app's `_pending` control key with its source keys. That is correct: the app then rebuilds unconditionally and derives its step-down state again from nothing. To delete **only** `_pending` does the opposite. It cancels a scheduled step-down retry, and does not force a rebuild. One config edit now changes the decision indirectly: a change to `arch` or to `included-patches` can make a recorded `_pending` target stale. Neither is a bundle change, so neither starts a rebuild by itself. The correction is the same key deletion.

- **Releases are immutable — deleting one burns its tag name for good.** Every published release in this repo carries `immutable: true` (`gh api repos/<r>/releases`). A deleted release frees the *release*, not the *name*: recreating the tag fails with `422 Reference update failed`, and publishing under it fails with `pre_receive … Cannot create ref due to creations being restricted / tag_name was used by an immutable release`. That bites hard because `NEXT_VER_CODE` is `latest release tag + 1`, so a single burned name **wedges every future run on the same number**, and it fails *late* — after the full build, at `Upload release`, with the artifacts stranded in an unpublishable draft. This happened in CI run **#92** (2026-08-31): release 48 had been deleted by hand to undo run #91's duplicate build, so #92 built all 3 apps correctly and then could not publish. `Get next version code` now **claims the tag up front** (`POST /git/refs`) and steps over any name that is taken or reserved, up to 20 tries; `gh release create` then uses the existing tag. **So: prefer editing or superseding a release over deleting one** — and if you do delete one, know that its number is spent and the next build will skip past it (leaving a gap in the sequence, which is harmless). Plain tags that were never an immutable release stay re-creatable after deletion; only release-backed names are burned.

- **The build-decision app list is computed once, in `ci.yml` — never in `build.yml` (fork-specific fix).** `build.yml`'s `Update config` step used to re-run `./build.sh config.toml --config-update` itself, but that step carried **no `GITHUB_TOKEN`**. Unauthenticated, `utils.sh`'s `GH_HEADER` is empty and every `api.github.com/.../releases/latest` lookup hits the shared-runner-IP rate limit with **HTTP 403**. `_patches_src_changed` returns non-zero on an unresolvable source — the deliberate "API error = no change" rule — so with *all* sources 403ing, `config_update` printed **nothing**, `config.json` was never written, and `Build modules/APKs` took its `else` branch: `./build.sh config.toml`, i.e. **the full config**. The safety rule was inverted at the workflow level: empty means "nothing to build" inside `build.sh` but meant "build everything" in `build.yml`. This detonated in CI run **#91** (2026-08-31) — the `check` job correctly picked 3 apps, the build job rebuilt all 9 buildable ones, and the 2 that actually needed it (Instagram, Twitter/X) failed for want of a mirrored APK. Now `check` (which *does* hold the token) passes its answer down as `update_cfg`, `build.yml` writes it straight to `config.json`, and an **empty** `update_cfg` on a CI-triggered build is a hard `exit 1` rather than a silent full rebuild. `ci.yml`'s old "first time building!" special case is gone with it: a missing state file makes `config_update` emit every enabled app anyway (verified), so the one code path covers both. A manual `workflow_dispatch` of **Build Modules** still builds the full `config.toml` — `inputs.from_ci` is unset there, so the `Update config` step is skipped.

- **Pinned-version apps drift against newer patches.** A literal `version =` passes `-f` to the CLI, which bypasses the *version-compatibility gate* but NOT per-patch fingerprint matching. A newer patch whose fingerprint isn't in the pinned APK hard-fails the whole build (`PatchException: Failed to match the fingerprint`). Fix by excluding that patch via `excluded-patches` or setting `patcher-args = "--continue-on-error"`. (Twitter *used* to pin `11.81.0` and exclude `'Block redirecting to X Lite'` for exactly this reason; it was then unpinned to `version = "auto"` by layering the **x-shim** bundle alongside Piko via `extra-patches-source`, which let both the pin and the X-Lite exclusion be dropped. x-shim has since been removed too — Piko no longer needs it (see the `extra-patches-source` note below) — so `["Twitter/X-Piko"]` is now plain `auto` + Piko alone. Instagram and Facebook likewise moved from a pin to `version = "auto"` — for Facebook, `auto` resolves to its bundle's only supported build, still served from the self-hosted archive.org mirror.)

- **`list-versions` version-code suffix (morphe-cli >= 1.14.0).** From 1.14.0 the CLI appends ` [versionCodes: ARM64_V8A=..., ARMEABI_V7A=...]` to each `Most common compatible versions:` line for bundles whose targets declare version codes. `_supported_vers_for_jar` used to pass that straight through, so `version = "auto"` resolved to e.g. `12.10.0[versionCodes:ARM64_V8A=70242,...]` (spaces stripped by `version_f`) and **no** download source could match it — `stock apk download failed` for every affected app. It now strips the suffix at the parse point. Which bundles declare version codes (checked with `list-versions --patches <mpp> -f <pkg>`): **Piko** (Instagram), **rushiranpise** (Telegram, Photos) → affected; Morphe (YouTube/Music/Reddit), Chiggi (Threads), Piko/Twitter, andrewliang25 (LINE, Facebook) print bare versions. De-Vanced/Photos used to print `Any`, which no longer applies. The last green CI run used CLI `1.13.2`, which doesn't emit the suffix — with `cli-version = latest` this would have broken those four apps on the next run regardless of the Telegram change.

- **`auto` step-down when the top version isn't downloadable (fork-specific addition).** A patch bundle can declare a version compatible that has no obtainable APK — historically, Paresh listed Telegram-web `org.telegram.messenger.web` `12.9.1`, which didn't exist (12.9.1 was only a Play-Store `org.telegram.messenger` build; the web build topped out at `12.8.3`). That app has since moved off Paresh (see the Telegram note below), but the mechanism stands. Rather than fail, `auto` now resolves the **full ranked list** of supported versions (`get_patch_last_supported_ver` → `_supported_vers_for_jar`, both in `utils.sh`, return highest-first) and `build_rv` tries them top-down: for each candidate it runs the normal all-sources download loop, and only steps to the next version once **no** configured source can serve the current one. This uses the download attempt itself as the availability oracle — correct across all download sources without pre-reconciling their (differently-formatted, sometimes partial) version lists. Non-`auto` modes resolve a single candidate, so the loop runs once (unchanged). **Safety guarantee — step-down never silently drops a patch:** `_supported_vers_for_jar` only ever returns versions tied at the **maximum** patch count (`grep "($pcount patch"` where `pcount` is the top line's count), so a lower version supporting *fewer* patches is filtered out and is never a step-down target — if the only downloadable version would lose patches, the build **fails loudly** instead of downgrading. (The lone residual, not handled: two versions at the *same* count but with *different* patch sets — the count summary can't distinguish them; no configured app exhibits this.) A successful step-down is **not silent**: `build_rv` calls `record_warning` (→ `build-warnings.txt`), which `build.sh` summarizes locally and `build.yml` posts to the admin Telegram + job summary (see the Telegram-notifications note), so a shipped-but-below-latest version is visible without digging through logs.

- **A stepped-down app retries automatically, but only once the missed version is actually downloadable (fork-specific addition).** A step-down was a dead end. The build *succeeded*, so `log_built_patches` recorded the current bundle asset and `_patches_src_changed` then reported "no change". The app stayed on the lower version until the bundle next bumped, and an upload of the missing APK to the mirror did nothing by itself. CI run **#95** (2026-09-02) hit this: `YouTube-Morphe` shipped `21.04.223` because `21.07.247` was not mirrored yet, and nothing retried it. Now `build_rv` records the missed version in `patches-state.json` as `_pending`, beside `log_built_patches` and under the same success-only rule. `config_update` then **probes** whether a configured source can serve that exact version, arch and dpi. It makes no download. It adds the app to the build list only on a proven hit. This is **not** a daily rebuild, and that is deliberate. A blind retry re-ships identical artifacts with a fresh `versionCode` every day. That is the churn `patches-state.json` exists to stop. The probe is `dl_available` plus the per-source `<src>_available`. It is exact for **archive** (one folder-listing GET, cached per URL, and the negative answer is cached too) and for **direct** (string test plus a HEAD). The archive probe reuses `archive_match_path`, the matcher `dl_archive` itself uses, so the probe and the download cannot drift. That matcher is fixed-string and `-`-bounded (`-<version>-<arch>`), because the version is interpolated. Without `-F`, the dots of the version were wildcards. Without the leading `-`, a mirrored `11.2.3` also satisfied a wanted `1.2.3`. That was a smaller problem while the match only chose which file to download. The same answer now decides whether a build runs at all. **apkmirror and uptodown answer "unknown", which counts as unavailable.** `dl_apkmirror` needs a release page, plus `apkmirror_search` over 40 htmlq rows, plus two more GETs. It answers 403 to CI anyway. Both `get_*_vers` are partial, free-form and arch-blind. Cost: **0 requests** on the normal path, because the probe runs only for an app that has a `_pending` *and* no bundle change. It costs 1 GET when it does run. There is **no "host is down, stop asking" latch**, and that is deliberate. To separate a dead host from a 404 on the folder of one app needs curl's exit code. `get_archive_resp` reads its body through a `$(…)` subshell, and that subshell loses the code. A latch that cannot make this separation lets one missing folder silence the probe for every app checked after it. The traded cost is bounded: at worst one connect timeout for each stepped-down app, on a day archive.org is already unreachable. **Residual risk, accepted:** if the probe says yes but the build then fails, it retries daily. That is harmless when patching hard-fails, because nothing ships and the daily failure alert *is* the alarm. It is real `versionCode` churn in the unlikely case of a listed-yet-unfetchable file. To bound it needs a retry counter, and the build job cannot read prior state: `patches-state.json` only reaches the workspace at `build.yml`'s `git checkout -f update`, after the build. A counter is feasible in `build.yml`'s merge jq, and is deferred until the loop is observed. Escape hatches: delete the app's `_pending` key on `update`, or pin `version`. `direct_available` does a HEAD for this same reason: a string test can never falsify itself, so a rotted `direct-dlurl` that still named the wanted version loops for ever. Note also that `config_update` **must not write to stdout**, because its stdout is the config `ci.yml` captures and `build.yml` writes verbatim to `config.json`. The probe path thus logs only through `epr` and `wpr` (stderr), and is never called inside `$(…)`, which also discards the response cache.

- **Instagram is arch-pinned to `arm64-v8a`, and the arch choice picks a different upstream artifact.** `dl_archive` greps the mirror's folder listing for `<version>-<arch>` and falls back to `-all` *only*, so a config `arch` that names no mirrored file finds nothing — `arch` is a mirror-filename selector here, not just a native-lib subset. The mirror holds `com.instagram.android-439.0.0.37.89-arm64-v8a.apkm` (apkmirror's `(arm64-v8a) (480dpi)` variant, 123 MB, 2 splits — `base.apk` + `split_config.xxhdpi.apk`, with the native libs inside `base.apk`; there is no `split_config.arm64_v8a.apk`), so the table is `arch = "arm64-v8a"`. This **reverses** the older `arch = "all"` rule, which existed because on `435.0.0.37.76` the mirror's `-arm64-v8a.apkm` (134 MB) was a genuinely different, unpatchable build that died on `Add settings` → `Failed to match the fingerprint: …ExperimentsGetMobileConfigSpecifier` (crimera/piko#1658, closed NOT_PLANNED) while `-all.apkm` (203 MB) patched fine. That was **variant-specific, not arch-specific**: verified 2026-08-31 against Piko 3.9.0, the 439 arm64 build applies **55/55** patches. Piko 3.9.0 in fact declares only `ARM64_V8A` in its `list-versions` version codes for this package. **apkmirror ships two different builds behind that one variant label**, and the version code tells them apart: versionCode **384510796** (205 MB, 7 splits — it also carries the `executorch`, `pytorch`, `heliumcore`, `heliumiab` and `spm` feature splits) and versionCode **384510827** (123 MB, 2 splits), both titled `Instagram 439.0.0.37.89 (arm64-v8a) (480dpi)`. **384510827 is the one the bundle targets and the one mirrored** — as with Telegram, match the version code, not just the version string. Both were tested and both apply 55/55, so here the mismatch was harmless, but do not rely on that. Note also that the release asset name changes from `instagram-piko-v<ver>-all.apk` to `-arm64-v8a.apk`. Re-check the variant, not the arch label, when Instagram fails on a fingerprint.

- **Apps apkmirror/uptodown won't serve (e.g. Instagram).** apkmirror increasingly 403s even from CI runners. Self-host the APK on an archive.org item and use the `archive` backend: files named `<pkg>-<version>-<arch>.apk[m]` inside a folder whose path *ends in the package name*, with `archive-dlurl` pointing at that folder. `.apkm` bundles are merged automatically. archive.org "folders" are just slashes in filenames — set them with `ia upload --remote-name=` / `ia move`, not the web uploader.

- **Signature verification is opt-in.** `check_sig` only verifies an APK if its package is listed in `sig.txt` (`<sha256> <pkg>` per line); unlisted packages are silently accepted. When adding an app, extract its official cert with `apksigner verify --print-certs` and take the value `check_sig` uses (lines starting `Signer`, containing `SHA-256`, `tail -1`), then add it. For multi-signer apps (key rotation, e.g. Instagram) that's the last signer's hash; for bundles, every split must verify to it.

- **`include-stock = "auto"` — genuine signature, split vs merged (fork-specific).** `auto` (the `build.sh` default is still `merged`) keeps each app's **original developer signature** in the root module wherever the source shape allows — which matters for apps with server-side integrity/signature checks (LINE, Meta apps). It resolves per source shape in `build_rv` (`utils.sh:1307`): a **bundle** source (`.apkm`/`.xapk`, leaving a `${stock_apk}.apkm` beside the merged apk) → **`split`**, installing the *original signed splits* un-merged so the signature survives; a **single-apk** source → **`merged`**, shipping the untouched apk that was never re-signed (already genuine). So only bundle-sourced apps change behavior vs the old `merged` default. Verified split-vs-merged against the archive.org mirror listing (archive is primary for every app): **split (`.apkm`) module apps = Reddit, Facebook (`com.facebook.katana`), Threads, LINE, Telegram (`org.telegram.messenger`)**; single-apk (`.apk`) = Photos, Music, YouTube; Twitter/X is `.apkm` + module → **split** (module re-enabled after the runtime issues that dropped it stopped reproducing); Instagram is `.apkm` but `build-mode = "apk"` (no module).

  **`include-stock` governs the *stock* apk only — the patched apk's signature is irrelevant in module mode.** The module **installs** `stock/*.apk` (`module/customize.sh:80-97`, `pm install-create`/`install-write`/`install-commit`) and then bind-mounts the patched apk over the installed `base.apk` (`module/customize.sh:147`). PackageManager records the signature at **install** time, from the stock apk; the mount lands afterwards at the filesystem layer, below the package manager. So the package keeps the stock apk's key no matter that `patch_apk` re-signed the patched one with `ks.keystore` — which is exactly why module mode excludes the microG patch. Non-root APKs are the opposite case and are untouched by `include-stock`: they are standalone `ks.keystore`-signed installs.

  **Which stock apk carries which key.** Only one of the three paths re-signs:
  - **bundle → `split`** — the original splits are unzipped straight out of the `.apkm` (`utils.sh:1311-1326`), never merged → **developer key**.
  - **single-apk → `merged`** — `cp -f "$stock_apk"`, never merged, never re-signed → **developer key**.
  - **bundle → `merged`** (the pre-`auto` default, and what an explicit `include-stock = "merged"` still does) — `merge_splits` runs APKEditor and re-signs with **`ks-p12.keystore`** (`utils.sh:643-648`) → **our key**.

  **Upgrade caveat — narrower than it looks; modules only.** A signing-key change happens *only* on the third path, i.e. when a **bundle-sourced** module moves off `merged`. That is the historical `merged` default → `auto` switch: Android then **refuses to install over an existing install** (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`), and users must uninstall first (clears data) before flashing. It is a **user-facing** caveat: put it in the **public** release notes / `build.md`, *not* through `record_warning` (that `build-warnings.txt` channel is admin-only — Telegram + job summary), and shipping it requires forcing those apps' rebuild (see "Forcing a rebuild"). **It does *not* apply when a source merely changes shape under `auto`** — e.g. Photos falling back from the archive `.apk` to an uptodown `.xapk` goes `merged` → `split`, but both ship a genuine-signed stock, so the key is unchanged and no reinstall is forced. What does change there is the install *shape* (`base.apk` plus `split_config.*` instead of one universal apk), which is an ordinary same-key update; `check_sig` verifies either shape against `sig.txt`.

- **The GmsCore/MicroG toggle covers *every* such patch of a bundle (fork-specific fix).** `build_rv` finds the bundle's GmsCore/MicroG patches by name (`grep -i "gmscore\|microg"` over `list-patches`) and toggles them per build mode: `-e` in **apk** mode, because a re-signed standalone apk loses the signature that Google APIs need, and `-d` in **module** mode, because the module mounts over the stock app and keeps its genuine signature. Config cannot override this — an `included-patches`/`excluded-patches` entry for such a patch only earns a warning. The detection used to be a **scalar**, which assumed one such patch per bundle (true of ReVanced/Morphe's single `GmsCore support (MicroG)`). `andrewliang25/morphe-patches` 2.0.0 ships **two** for LINE (`Fix location maps via GmsCore`, `Fix chat backup sign-in via GmsCore`), so `grep` returned both lines and `${var#*: }` stripped only the first `Name: ` prefix: one newline-joined string that matches no patch name. morphe-cli **ignores an unknown `-e`/`-d` silently** (exit 0, no warning), so the LINE **module** would have shipped with both GmsCore patches enabled and nothing in the log to say so. `microg_patches` is now an array, looped at all three use sites (the include/exclude guard, the per-mode filename suffix, and the `-e`/`-d` append). Two things to know if you touch this: the strip in the guard (`${p_patcher_args[@]//-[ei] ${mgp}/}`) has never actually matched, because `join_args` emits `-e 'Name'` **with quotes** — it is left as upstream wrote it, since making it match could leave a dangling `'Other'` token from a multi-name `-e 'A' 'B'` group; and detection is by patch **name**, so a GmsCore patch named without either word is invisible to it.

- **morphe-cli silently drops a `-O` that follows a `-e` in the same `-p` group (verified on 1.15.1).** `patch`'s picocli group is `(-p=<file> [[[-O=<k=v>]... (-e=<name>)] [(-d=<name>)]]...)...`, but in practice only the `-O` flags that come **before the first `-e` of the group** are bound; every later one is dropped with **no warning and exit 0** — the same silent-ignore behavior as an unknown `-e`/`-d`. Verified with two controlled runs against Photos + rushiranpise 1.21.5: `-O googlePhotosPackageName=app.otest.photos -e 'Change package name'` produced `package="app.otest.photos"`, while `-e 'GmsCore support' -O googlePhotosPackageName=app.otest2.photos -e 'Change package name'` produced the patch default. This matters because `build_rv` appends the clone override **after** the microg `-e`s (`patcher_args+=("-O packageName=${clone_pkg} -e \"${clone_patch}\"")`), so for any app whose bundle ships **both** a GmsCore/MicroG patch and a clone patch, `clone_pkg` never reaches the CLI and the rename falls back to whatever the patch defaults to. **Photos is the only such app** — checked 2026-09-12 across every configured bundle: Chiggi (barcelona), Piko (instagram) and Morphe (reddit) each ship a rename patch but **no** gmscore/microg patch, so their `-O` is the first of its group and binds. (andrewliang25/katana ships neither, so it is not a case at all.) The drop is not new with the bundle switch: the last shipped **De-Vanced** Photos APK (release 54, `7.85.0.952162352`) is already `app.morphe.android.apps.photos`, i.e. De-Vanced's own `packageName` default, not the `app.devanced.google.android.apps.photos` that `build_rv` asked for and that the README used to claim. Fixing it needs two changes, not one — move the clone `-O ... -e` ahead of the microg `-e`s **and** stop assuming the option key is `packageName` (Photos/Rushi uses `googlePhotosPackageName`; Photos/De-Vanced used `packageName`) — and the fix would change the shipped package, forcing a reinstall. Deferred for that reason. Note `patcher-args` cannot work around it either: `p_patcher_args` puts `excluded-patches`/`included-patches` first, so a `-O` from config lands after those `-e`s, or else binds to the wrong (first) patch.

- **Google Photos (`com.google.android.apps.photos`) — rushiranpise, `build-mode = "both"` + `clone = true`.** Moved off `RookieEnough/De-Vanced` to [`rushiranpise/morphe-patches`](https://github.com/rushiranpise/morphe-patches) (the same bundle Telegram uses), so `rv-brand` is `Rushi` and the table is `[Photos-Rushi]`. `version = "auto"` resolves to the bundle's single target **7.90.0.971743778** (versionCode **52288898**, universal `-all` apk, one entry in `list-versions`). Because it is the only supported version there is **no step-down target**, so a missing mirror upload fails the build loudly rather than shipping an older build — the archive.org item must carry `com.google.android.apps.photos-7.90.0.971743778-all.apk` or the build dies at `stock apk download failed`. 6 patches apply in apk mode: `Change package name`, `Enable DCIM folders backup control`, `Fix DCIM folder classification`, `GmsCore support`, `GmsCore support (MicroG)`, `Spoof features` (`AMOLED dark theme` ships default-off). Three things differ from De-Vanced:
  - **`Change package name` is default-*enabled* here.** `build_rv` only ever `-e`s a clone patch in apk mode; it never `-d`s one. Left alone the **module** would ship a renamed package and could not mount over stock, so the table carries `module-excluded-patches = "'Change package name'"` — the same workaround `[Threads-Chiggi]` already uses for the same reason.
  - **Two gmscore patches, and both are wanted.** The bundle ships a Photos-specific `GmsCore support` (metadata) *and* the universal `GmsCore support (MicroG)` (the actual routing, which logs `getGmsCoreVendorGroupId() patched → "app.revanced"`). They are complementary, not duplicates, and apply cleanly together; the microg-array handling added for LINE covers them.
  - **The clone package comes from the patch, not from `build_rv`.** Its option key is `googlePhotosPackageName` (default `app.morphe.android.apps.photos`, launcher name `Photos Morphe`), not `packageName`, and the override is dropped anyway — see the `-O` ordering note above. The shipped package is therefore **unchanged** from the De-Vanced era, so the non-root APK updates in place; only the module id changes (`photos-devanced-andrew` → `photos-rushi-andrew`), which Magisk treats as a new module.

- **Module id must be Magisk-legal — table names with `/` or `+` are not (fork-specific fix).** The module id defaults to the table name lowercased plus `-andrew` (`build.sh`), and Magisk validates it at *flash* time against `^[a-zA-Z][a-zA-Z0-9._-]+$`, refusing the zip with `Invalid module ID in module.prop` otherwise. `["Twitter/X-Piko"]` therefore produced `twitter/x-piko-andrew` and was unflashable — a latent trap the whole time the table was `build-mode = "apk"` (no module.prop is generated in apk mode), which detonated the moment the module was re-enabled. Note the build itself succeeds and CI ships the broken zip; only the on-device flash fails. Now `module_id_name` (`utils.sh`, beside the pre-existing `update_json_name`, which already folded `/` for the same reason) folds every character outside `[a-z0-9._-]` to `-`, and `build.sh` aborts on an id that still fails the regex — which also guards a hand-set `module-prop-name`. Only slash/plus tables change id; every other app's module id is byte-identical, so no module churn for users. **Changing a module id makes Magisk see a brand-new module**, so a fixed id installs alongside the old entry rather than updating it (harmless here — the broken one could never install).

- **Local testing on macOS.** The `bin/*-arm64` / `*-arm` helper binaries are Android/Bionic builds and won't run on macOS or Linux; the `-x86_64` ones are glibc Linux. To run a build locally, use a `linux/amd64` Docker container (`ubuntu`, `apt install jq openjdk-21-jre-headless zip unzip curl`, repo mounted at `/repo`) so `set_prebuilts` selects the working x86_64 binaries. Use **openjdk-21**, not 17 — the Morphe CLI needs Java 21 (see the requirements note above). When mounting the repo, note that `TEMP_DIR`/`BUILD_DIR` are hardcoded relative paths (`temp`/`build`): a build writes into the mounted tree and reuses any stale `temp/`/`build/` already there, so for a clean isolated run `rsync -a --exclude build --exclude temp --exclude .git /repo/ /work/` into a container-local dir and build from `/work`.

- **`clone = true` (fork-specific addition).** Non-upstream config option in `build_rv`. For a `build-mode = "both"` app it generalizes the microG hook: in **apk** mode it enables the rename patch (the first of `Clone`, `Clone app`, `Change package name` that the bundle ships) with `-O packageName=app.<brand>.<pkg-without-com>`, producing a coexisting clone APK; in **module** mode it omits it, keeping the original package for mounting. So one entry yields both a clone APK and an original-package module (Threads/Instagram/Photos). The brand = `rv-brand` lowercased, non-alphanumerics stripped (De-Vanced→devanced).

- **`extra-patches-source` (fork-specific addition) — currently unused.** Optional per-app key for applying a *second* patch bundle in the same patch run. Its only user was Twitter/X (`gitlab:inotia00/x-shim` together with `crimera/piko` — Piko's "X-Shim + Piko" flow); that was **removed** because Piko's README now states that starting `12.5.0-release.0` x-shim need not be applied alongside Piko (X login and XChat work without it). The machinery below is kept — it's inert when the key is unset (`app_args[ptjar_extra]=""`) and the same shim-alongside-primary situation is likely to recur. `build.sh` fetches it by reusing `get_prebuilts` (so `gitlab:`/GitHub + integrations-check stripping all work; the CLI is already cached from the primary fetch) into `app_args[ptjar_extra]`; `patch_apk` appends one extra `-p` per bundle (space-separated → N-capable). Version/`auto` resolution and the module name/changelog stay on the **primary** bundle; the extra bundle's patches are default-enabled and apply without enumeration. Crucially, `build_rv` records the extra bundle's built asset into `patches-state.json` under its own source key (`log_built_patches` is called once for the primary and once for the extra), and `config_update` compares `extra-patches-source` independently (via `_patches_src_changed`, run for both primary and extra), so a new release of the extra bundle **self-triggers a daily rebuild** — it doesn't have to wait for a primary-bundle bump. `extra-patches-version` defaults to `latest`.

- **Twitter/X can't be cloned — don't add `clone = true` to it** (it *does* ship a module, though — `build-mode = "both"`). Verified against the configured bundle: Piko (`crimera/piko`) *does* ship a `Clone` patch, but its `compatiblePackages` is **`com.instagram.android` only** — which is why `Instagram-Piko` clones to `app.piko.instagram.android` but X never could. (Note too that the clone detector enumerates only the **primary** bundle's patch list, filtered by `--filter-package-name com.twitter.android` — built by `patches_list` and scanned by the clone grep, both in `build_rv` — so a rename patch supplied via `extra-patches-source` would not be picked up even if one existed.) (Piko's README also warns against layering Morphe's universal `Change package name` patch on top of Piko.) So Twitter/X stays un-cloned: both its non-root APK and its module keep `com.twitter.android`, shared with the Play Store build (users switching from the APK to the module must uninstall the APK first — different signing key on the same package).

- **Facebook (`com.facebook.katana`) — andrewliang25, `build-mode = "both"`, no clone.** Moved off `RookieEnough/De-Vanced` to [`andrewliang25/morphe-patches`](https://github.com/andrewliang25/morphe-patches), the same bundle LINE uses. Thus `rv-brand` is `Andrew` and the table is `[Facebook-Andrew]`. The bundle ships **7 katana patches, and every one is default-enabled**: `[Ad] Block background ad prefetch`, `[Ad] Block ad telemetry`, `[Ad] Disable Audience Network`, `[Feed] Hide sponsored posts`, `[Feed] Hide suggested and promoted posts`, `[Reels] Hide sponsored reels`, `[Stories] Hide sponsored stories`. No `excluded-patches` is necessary. The move has three consequences:
  - **`version = "auto"` has one target, `577.0.0.50.72`, and thus no step-down target.** As with Photos, a missing mirror upload fails the build loudly. It does not ship an older build. The folder `apks/com.facebook.katana/` must carry `com.facebook.katana-577.0.0.50.72-arm64-v8a.apkm`. The older `490.0.0.63.82` upload (the De-Vanced target) is not used any more. **uptodown cannot serve this build.** It lists `577.0.0.50.72`, but `dl_uptodown` finds no `arm64-v8a` variant and fails with a 404 (verified 2026-09-15 with a direct call to the function). Thus archive is the only source that works.
  - **`clone = true` was removed, because the bundle has no rename patch for katana.** The key does nothing here, because the bundle ships none of the three rename-patch names the detector knows. Reddit *used* to be inert for the same reason and no longer is — see the rename-patch note below. The key also implies a clone that never ships. So the non-root APK keeps `com.facebook.katana` and **replaces** the official app. The two cannot coexist. This is a user-facing caveat for the release notes, the same one that Telegram, LINE and Reddit carry.
  - **The bundle has no gmscore/microg patch for katana.** Thus the APK needs no MicroG-RE, and the `-O`-after-`-e` ordering trap does not apply to it.

  The table rename `[Facebook-DeVanced]` → `[Facebook-Andrew]` changes the module id from `facebook-devanced-andrew` to `facebook-andrew-andrew`. **Magisk sees that as a new module.** It installs beside the old entry, and it does not update that entry. The rename also changes the release asset names to `facebook-andrew-*` and the `patches-state.json` key, so the app rebuilds unconditionally on the next run. De-Vanced (`RookieEnough/De-Vanced`) now has **no configured app at all**, because Messenger was dropped and Facebook moved. Thus nothing fetches that bundle any more.

- **The clone detector matches the rename patch by exact name, and each bundle picks a different one.** `build_rv` takes the first of **`Clone`** (Piko), **`Clone app`** (Morphe), **`Change package name`** (Chiggi, Rushi) that the bundle's `list-patches` prints. All three take the option key `packageName`. It used to try `Clone` and `Change package name` only, so when Morphe renamed its universal rename patch to `Clone app`, `[Reddit-Morphe]`'s `clone = true` went **inert**: the build logged one `clone=true but no … patch found` line and shipped `com.reddit.frontpage` instead of `app.morphe.reddit.frontpage`. It is one `epr` line in a green build, so it went unnoticed through releases 61 and 67 (both verified with `apkeditor info`). Unlike a config-named patch, this one the builder names itself, so `list-patches` after a bundle bump has to be checked against **this list too**, not only against `config.toml`. Verified 2026-09-22 with morphe-cli 1.16.0 + Morphe patches 1.44.0 on stock Reddit `2026.14.0`: `INFO: Applied: Clone app`, and the output manifest reads `package="app.morphe.reddit.frontpage"`. **The rename is user-facing** — the non-root Reddit APK changes package, so Android cannot update an APK from release 67 or earlier onto it and users must uninstall first. That belongs in the public release notes, not in `record_warning`. The module is unaffected: the rename patch stays off in module mode.

- **A bundle-wide patch rename silently breaks config that names patches (andrewliang25 v3.0.0, 2026-09-15).** v3.0.0 renamed **every** patch in the bundle to a `[Category] Name` form. For LINE, `Fix push notifications` became `[Fix] Restore push notifications`. The two GmsCore patches became `[Fix] Restore location maps via MicroG-RE` and `[Fix] Restore chat backup sign-in via MicroG-RE`. morphe-cli **ignores an unknown `-e`/`-d` with exit 0 and no warning**. Thus, without this correction, the `apk-included-patches` and `module-excluded-patches` keys of `[LINE-Andrew]` match no patch on the next run. The APK loses the push fix, and the module *gains* it, because the patch is default-enabled. Nothing in the log says so. Both keys now use the new name. Two things did **not** break. The microg detection is a `grep -i "gmscore\|microg"` over `list-patches`, and the new names still contain "MicroG". Thus it still finds both LINE patches, and it passes the current names to `-e`/`-d`. A bracketed name also survives `toml_get` → `list_args` → `join_args`, and the result is `-e "[Fix] Restore push notifications"` (verified with a direct call to the functions). **The general rule: a patch name in `config.toml` is a string contract with the bundle, and the CLI does not tell you when it breaks.** After a major version change of a bundle, compare `list-patches` with every name that the config holds.
